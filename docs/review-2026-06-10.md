# ForkScale — Senior Architecture & Code Review

**Date:** 2026-06-10
**Scope:** Full `fork_scale/lib` source (38 Dart files), `pubspec.yaml`, AndroidManifest, test suite.
**Method:** Manual line-by-line review + `flutter analyze` (clean — all findings below are beyond lint level).

Severity legend: 🔴 **Critical** (data loss / security) · 🟠 **High** (user-visible bug or real risk) · 🟡 **Medium** (degraded quality, latent bug) · ⚪ **Low** (hygiene / polish)

---

## 1. Executive summary

The app is in decent shape for a fast-moving solo project: clear feature folders, repository layer over sqflite, Riverpod for DI, deliberate small touches (truncated-JSON repair, photo ref-counting on delete, camera lifecycle handling). However, the review found **two critical issues** (a zip-slip vulnerability in backup restore, and foreign-key cascades that silently never run, so child rows are orphaned forever), a **cluster of high-severity correctness bugs** (UTC vs. local-time day bucketing skews streaks/insights for a Swiss user; a modal sheet that can never display its search results; no transactions around multi-statement writes), and systemic patterns that will increasingly hurt: N+1 queries, copy-pasted widgets drifting apart, manual provider-invalidation webs, and a `copyWith` design that makes "clear this field" impossible to persist.

Top 5 actions, in order:

1. Sanitize entry paths in `BackupService.restoreBackup` (zip-slip). — §3.1
2. Enable `PRAGMA foreign_keys = ON` (or delete child rows explicitly) and wrap multi-statement writes in transactions. — §4.1, §4.2
3. Unify day-bucketing to local time across all aggregate queries. — §4.3
4. Fix the add-ingredient sheet rebuild bug (search results never appear). — §5.1
5. Re-encrypt the Gemini key (or at minimum set `android:allowBackup="false"`). — §3.2

## 2. Architecture overview (as-built)

```
lib/
  core/
    database/    AppDatabase (static singleton) + 3 repositories
    services/    Gemini, OFF, USDA, SFCD, image, backup + providers.dart
```

## 3. Security

### 3.1 🔴 Zip-slip (path traversal) in backup restore
`backup_service.dart:58-64` — entries from a user-picked zip are written to `p.join(docs.path, file.name)` with no sanitization. A crafted archive with entries like `..\..\shared_prefs\FlutterSharedPreferences.xml` writes **outside** the documents directory — on Android that reaches the entire app sandbox (prefs, databases), enabling config/key overwrite. Restore is exactly the place users feed in files they got from somewhere else.

**Fix:** resolve the output path and verify it stays under `docs.path` before writing:

```dart
final outPath = p.normalize(p.join(docs.path, file.name));
if (!p.isWithin(docs.path, outPath)) continue; // or throw
```

### 3.2 🔴→🟠 Gemini API key stored in plaintext SharedPreferences, and backups are enabled
`settings_screen.dart:62-77` deliberately migrates the key **out of** `flutter_secure_storage` **into** `SharedPreferences` (pubspec comment confirms). On its own that's app-sandbox-only, but `AndroidManifest.xml` does **not** set `android:allowBackup="false"` / `dataExtractionRules`, so the plaintext key is included in device-to-device transfers and `adb backup`-class extraction paths. Combined effect: a billing-sensitive credential at rest in plaintext XML that leaves the device.

**Fix (cheapest acceptable):** keep the key where it is but set `android:allowBackup="false"` and add `dataExtractionRules` excluding shared prefs. Better: return to `flutter_secure_storage` (the package is still a dependency — you're paying its cost without its benefit).

### 3.3 🟠 API key passed as URL query parameter
`gemini_service.dart:96` (`?key=$apiKey`) and `:190`. Query strings end up in proxy logs, corporate TLS-inspection logs, and any error/telemetry capturing the URL. Google supports the `x-goog-api-key` **header** for the same endpoint.

### 3.4 🟡 Unbounded zip decode on restore
`backup_service.dart:55-56` — `ZipDecoder().decodeBytes(await File(...).readAsBytes())` loads the whole archive **and** its decompressed contents into memory. A decompression bomb (or just a multi-GB legit backup of photos) OOM-kills the app mid-restore — and because restore is non-transactional file-by-file overwriting, a crash midway leaves a half-restored data directory. Use the streaming `InputFileStream`/`extractArchiveToDisk` APIs and cap entry sizes.

### 3.5 🟡 CSV formula injection in export
`meals_repository.dart:303-323` — item names (LLM- or user-supplied) are embedded into a CSV that users open in Excel/Sheets. A name like `=HYPERLINK(...)` executes as a formula. Prefix cells starting with `=`, `+`, `-`, `@` with `'` when exporting.

### 3.6 ⚪ Raw FTS `MATCH` on user input
`meals_repository.dart:250-253` — the search string goes into `MATCH ?` unescaped. Parameterization prevents SQL injection, but FTS4 has its own query syntax: input like `"unclosed` or `AND` throws `SqliteException`, surfacing as the history screen's error state. Wrap user input in quotes / strip FTS operators.

### 3.7 ⚪ Notes
- Barcode input is regex-validated before use (`barcode_scanner_screen.dart:33`) — good.
- `image_service.downloadAndSave` fetches whatever URL OFF returns without scheme/host validation; low risk (HTTPS API, cleartext blocked by modern Android defaults) but a `https`-scheme check is one line.
- Error-detail dialogs (`capture_screen.dart:250`) show raw API response bodies; acceptable for a personal tool, reconsider before distribution.

## 4. Data integrity & correctness

### 4.1 🔴 Foreign-key cascades never run → permanent orphan rows
The schema relies on `ON DELETE CASCADE` (`meal_items`, `recipe_items`) and `ON DELETE SET NULL` (`meals.recipe_id`), but **sqflite does not enable foreign keys by default** and nothing in `app_database.dart` issues `PRAGMA foreign_keys = ON` (verified: no `onConfigure` / pragma anywhere).

Consequences today:
- `deleteMeal` (`meals_repository.dart:53-69`) deletes the `meals` row and the FTS row but **never deletes `meal_items`** — every deleted meal leaks its items forever.
- `deleteRecipe` (`recipes_repository.dart:29-32`) leaks `recipe_items` the same way.
- Deleting a recipe leaves `meals.recipe_id` dangling instead of `SET NULL` (UI happens to tolerate the missing recipe, but the constraint is dead weight).

**Fix:** add to `openDatabase`:

```dart
onConfigure: (db) => db.execute('PRAGMA foreign_keys = ON'),
```

…and add a one-time cleanup migration deleting already-orphaned rows.

### 4.2 🔴 No transactions around multi-statement writes
`grep transaction lib/` → zero hits. Every compound write is a sequence of independent auto-committed statements:
- `insertMeal` = insert meal → N item inserts → FTS insert (`meals_repository.dart:25-37`)
- `updateMeal` = update → delete all items → re-insert all items → FTS (`:39-51`)
- `insertRecipe`/`updateRecipe` same pattern.

A crash or exception mid-sequence leaves a meal with half its items, or a recipe whose items were deleted but not re-inserted (the `updateRecipe` delete-then-insert window is the worst). Wrap each in `db.transaction((txn) async { ... })` — this is also a large performance win (§6.5).

### 4.3 🟠 UTC vs. local-time day bucketing — insights are wrong for a UTC+1 user
Two different "what day is this meal" definitions coexist:
- **Local time:** `getDayTotalKcal`, `getWeeklyKcal`, `getMealNamesToday` (Dart `DateTime` ranges).
- **UTC:** `getAvgDailyKcal`, `getAvgDailyMacros`, `getDaysOverGoal`, `getDaysWithMeals`, `getCurrentStreak` — all group by `strftime('%Y-%m-%d', datetime(created_at/1000, 'unixepoch'))`, which is UTC (`meals_repository.dart:340, 358, 392, 425, 438`).

For Switzerland (UTC+1/+2), any meal logged after 22:00–23:00 lands on the **next** UTC day. Effects: the weekly chart and "daily average" disagree; `getCurrentStreak` compares UTC-day strings against locally-formatted day strings (`:397-414`) so a dinner-only logging habit can show a broken streak that the chart contradicts. Fix by appending `'localtime'` to the `datetime()` calls, or grouping in Dart.

### 4.4 🟠 Backup of a live SQLite file; restore leaves stale WAL sidecars
`createBackup` (`backup_service.dart:23-26`) zips `fork_scale.db` **while the connection is open**, without a checkpoint — recent transactions living in `-wal` are silently missing from the backup. `restoreBackup` closes connections (good) but doesn't delete leftover `fork_scale.db-wal` / `-shm` from the old database; on next open SQLite may replay an old WAL against the restored file — corruption territory. Checkpoint (`PRAGMA wal_checkpoint(TRUNCATE)`) or close before zipping; delete `-wal`/`-shm` on restore.

### 4.5 🟠 `clearHistory` deletes the DB file under an open connection
`settings_screen.dart:250-256` deletes `fork_scale.db` without calling `AppDatabase.closeAll()`. The open connection keeps writing into the unlinked inode; the app appears to work until restart, then everything vanishes — matching the "Restart the app" snackbar, but any meal logged between clear and restart is silently lost. It also never invalidates providers or deletes WAL sidecars. Close → delete (incl. `-wal`/`-shm`) → invalidate, and offer in-app reload instead of demanding a restart.

### 4.6 🟠 `copyWith` null-trap: clearing a field can never be persisted
All models use `field: x ?? this.field`. Therefore `meal.copyWith(notes: null)` **keeps the old notes**. Concrete user-visible bug: in `MealEditScreen._save` (`meal_edit_screen.dart:84-92`) clearing the notes field passes `notes: null` → old notes survive the save. Same trap is latent for `mealType`, `scaleConf`, etc. The team already knows about the problem — `IngredientCard._emitMacros` (`ingredient_card.dart:64-79`) rebuilds the object field-by-field specifically to dodge it, in two copies. Adopt `freezed` (or sentinel-based copyWith) instead of growing workaround copies.

### 4.7 🟡 `usdaMatched` is not persisted
`meal_items` has no `usda_matched` column; `MealItem.fromMap` defaults it to `false`. After reload, every item — including USDA-verified ones — shows the "Calorie value from AI" flask tooltip in the editor. Either persist the flag or drop the pretense.

### 4.8 🟡 Schema duplicated between `onCreate` and `onUpgrade`
`app_database.dart` repeats full `CREATE TABLE` bodies in the v4 upgrade block. Two sources of truth always drift (the v4 copy already lacks the macro columns that v5/v6 patch in — currently consistent, but only by careful bookkeeping). Standard fix: `onCreate` = run all migrations from 0, so the schema is defined exactly once.

### 4.9 ⚪ Smaller items
- `getMeals` day ranges end at `23:59:59` — drops the last second's millis. Use `< nextDayStart` instead of `BETWEEN`.
- Stale `cached_products` rows are treated as missing but never evicted or refreshed-in-place (`products_repository.dart:16-19`); harmless, just untidy.
- `Meal.photoPath` uses `''` as a "no photo" sentinel on a `NOT NULL` column (barcode/manual meals). A nullable column states the intent.

## 5. Functional bugs (state & UI)

### 5.1 🟠 Add-ingredient sheet never shows search results
`recipe_editor_screen.dart:339-384` — `_showAddIngredientSheet` builds a **stateless** `_AddIngredientSheet` whose `searchResults`/`searching` come from the parent screen's state. `_searchSfcd` updates that state with `setState`, but a modal bottom sheet is a separate route: the parent's `setState` does **not** re-run the sheet's builder. Result: the user types, queries actually run against SFCD, and the sheet keeps showing its initial empty state — the food-database search path looks permanently broken; only "Scan barcode" and "Enter manually" work. Fix: make the sheet a `StatefulWidget` owning its own query state (also the natural home for the missing debounce, §6.6).

### 5.2 🟠 Index-keyed ingredient cards show stale data after deletion
`results_screen.dart:128` and `meal_edit_screen.dart:113` key cards by position (`ValueKey('item_$i')` / `'edit_$i'`). `IngredientCard` seeds `late final` controllers from `widget.item` in `initState` and has no `didUpdateWidget`. Delete item 0 of 3: item 1 now renders under key `item_0`, reusing the deleted item's State — name/weight/kcal text fields still show the **deleted** item's values while totals compute from the new one. Key by a stable identity (item id / generated uuid) and/or implement `didUpdateWidget` to resync controllers.

### 5.3 🟡 `ResultsNotifier.deleteItem` doesn't remap `editedIndices`
`results_notifier.dart:76-79` removes the item but keeps edited indices as-is, so the "edited" badge jumps to the wrong row after a deletion. `MealEditScreen._deleteItem` (`meal_edit_screen.dart:57-66`) implements the remap correctly — the same logic exists twice and has already diverged, one copy buggy.

### 5.4 🟡 Dead provider override — two notifiers per results screen
`results_screen.dart:26-31` creates a local provider in `initState`; `build` (`:81-84`) **additionally** wraps the body in a `ProviderScope` overriding the global `resultsNotifierProvider` — which nothing reads. Two `ResultsNotifier` instances are constructed; the override and the `resultsNotifierProvider` throw-stub (`results_notifier.dart:102-105`) are dead code. Pick one mechanism.

### 5.5 🟡 Stale history/insights after logging from the Capture tab
`StatefulShellRoute.indexedStack` keeps every branch alive, so the History tab's `autoDispose` providers stay watched and never refetch on tab switch. Logging via the recent-meals strip (`capture_screen.dart:423-433`) invalidates only `_recentMealsProvider`; `_savePending` (`:198`) invalidates nothing. The day-total bar, weekly chart and meal list on the History tab silently show pre-log values until a manual pull elsewhere triggers `onRefresh`. This is the structural cost of the manual-invalidation web — see §7.1.

### 5.6 🟡 Orphaned photo files when analysis fails
`capture_screen.dart:130-136` saves the history-sized photo to disk **before** the API call. On parse errors and generic failures no meal row is created, `_pendingSavedPath` isn't offered for save, and the file is never deleted — every failed analysis leaks a ~150-300 KB JPEG. `ImageService.deletePhoto` exists and has **zero callers** (verified by grep). Delete on non-retryable failure.

### 5.7 🟡 Settings screen: throwaway controller + recomputed storage scan
- `settings_screen.dart:320-321` creates a `TextEditingController` inline in `build` for the daily goal: never disposed (leak), recreated on every rebuild (cursor jumps to start while typing as soon as anything else triggers `setState`).
- `:412-417` calls `_storageSummary()` directly in `build` via `FutureBuilder` — every rebuild (each keystroke in any field on the screen) re-lists the entire photo directory and re-stats files.

### 5.8 🟡 Pepesto price integration is dead UI
The settings screen collects and validates a "Pepesto API key", `pepestoApiKeyProvider` exposes it, the schema has `price_chf` — and **no code anywhere uses either** (verified by grep: the key is written/read only by settings; `price_chf` is written only as a copy of itself). Users are being asked for a credential that does nothing. Remove the section or ship the feature.

## 6. Performance

### 6.1 🟠 N+1 query patterns throughout the data layer
- `getMeals` runs one query for meals + **one query per meal** for items (`meals_repository.dart:202-208`); at the default `limit: 50` that's 51 round-trips per history refresh.
- `_searchMeals` is worse: FTS query, then `getMeal(id)` per hit = 2 queries per result (`:256-261`).
- `getAllRecipes` (`recipes_repository.dart:42-51`) and `exportCsv` (`meals_repository.dart:305-307`) — same shape.

Fetch all items with one `WHERE meal_id IN (...)` (or a join) and group in Dart.

### 6.2 🟡 `getWeeklyKcal` = 7 separate aggregate queries
`meals_repository.dart:279-288` loops `getDayTotalKcal` per day. One `GROUP BY` over a 7-day range does it in a single query — and fixing it together with §4.3 keeps chart and averages consistent by construction.

### 6.3 🟡 Each capture decodes the full-resolution photo twice
`capture_screen.dart:130-133` runs `resizeForApi` and `saveForHistory` in parallel; each calls `img.decodeImage` on the same multi-MB original in its own isolate — double CPU and double peak memory at the exact moment the camera pipeline is also holding buffers. Decode once, then encode at 1536 and 1200 from the in-memory image (and the 1200px version could be derived from the 1536px one).

### 6.4 🟡 History thumbnails decode full-size images
`history_screen.dart:553` renders `Image.file(file, width: 56, height: 56)` without `cacheWidth`/`cacheHeight`. Every visible row decodes a 1200px JPEG to paint 56 logical pixels — classic list jank + bitmap-cache pressure. Add `cacheWidth: 112` (2x DPR). Same applies to detail/recipe headers to a lesser degree.

### 6.5 🟡 Row-by-row inserts, each in its own implicit transaction
A 10-ingredient recipe update = 1 update + 1 delete + 10 inserts = 12 fsync-bearing commits. The `db.transaction` fix from §4.2 collapses this to one; use `Batch` for the item loops.

### 6.6 🟡 SFCD search: a new DB connection per keystroke, never closed, no debounce
`SfcdService.search` (`sfcd_service.dart:24`) calls `AppDatabase.openSfcdDb()` on **every call**, and `openSfcdDb` (`app_database.dart:221-234`) opens a fresh `Database` each time (unlike `usdaDb`, which is cached) — connections are never closed. The recipe editor fires a search per keystroke with no debounce (`recipe_editor_screen.dart:160`, grep confirms no `Timer`/debounce in the codebase). Typing "zucchini" = 8 leaked connections and 8 `LIKE %…%` scans. Cache the handle like `usdaDb` and debounce ~300 ms.

### 6.7 ⚪ Smaller items
- USDA enrichment runs sequentially per item (`gemini_service.dart:151-169`), each a `LIKE '%w%'` full scan (non-sargable; no index can help). Fine at 5 items, but an FTS table on `foods.description` would be the right structure.
- `File.existsSync()` inside `build` methods (history tiles, photo headers, recipe cards) is synchronous I/O on the UI thread, once per row per frame rebuild.
- `getRecentDistinct` fetches 50 rows to pick 5 distinct names in Dart — `GROUP BY name` does it in SQL.

## 7. Architecture & design patterns

### 7.1 🟠 Two state philosophies stitched together with manual invalidation
Half the app is provider-driven (`FutureProvider.autoDispose` per screen), half is `StatefulWidget` + `setState` (settings, barcode result, meal builder, recipe editor). The seam is a hand-maintained invalidation web: the trio `historyMealsProvider` / `historyDayTotalProvider` / `historyWeeklyKcalProvider` is invalidated in **four** different files after writes — and still missed in at least two paths (§5.5). Every new write path must remember every affected provider; the design guarantees future staleness bugs.

**Recommendation:** make the repository the single change-source. Cheapest: a `ChangeNotifier`/`StreamController` "meals revision" the repositories bump on every write, with all read providers watching it. Cleaner long-term: stream-based queries (drift) so screens can't be stale by construction.

### 7.2 🟡 Inconsistent service construction bypasses DI
`geminiServiceProvider` exists, but `CaptureScreen._analyse` (`capture_screen.dart:117-122`) constructs `GeminiService(apiKey: apiKey)` directly while `MealDetailScreen` uses the provider — two code paths to the same dependency, one untestable. `GeminiService` also news up its own `UsdaService` default. Repositories are concrete classes with static-singleton DB access, so nothing in the data layer is fake-able in tests (§9).

### 7.3 🟡 Copy-paste widget duplication is already diverging
Catalogue (all near-identical):
- Meal-type chip row: 5 copies (`results_screen.dart`, `meal_edit_screen.dart`, `barcode_result_screen.dart`, `barcode_meal_builder_screen.dart`, `log_portion_sheet.dart`) — already styled differently (primary vs. accent selection).
- `_mealTypeLabel`: 3 copies. `_macroLine`: 2. `_PhotoHeader`: 2. `_TotalBanner`, `_SaveBar`, `_NotesField`: 2 each. `_autoName`: 2. Amount stepper (± buttons + field): 4 variants.
- The big one: `_IngredientRow` (recipe editor, ~230 lines) vs. `IngredientCard` (results, ~300 lines) are the same component for two models — including the same duplicated `_emitMacros` workaround. §5.3 shows duplicated *logic* already diverging with one copy buggy.

Extract a `widgets/` layer (`MealTypeSelector`, `AmountStepper`, `PhotoHeader`, a generic ingredient editor over a small interface).

### 7.4 🟡 Stringly-typed domain
`'camera' | 'barcode' | 'recipe_portion'`, `'fork' | 'knife' | 'spoon'`, meal types, `'off' | 'swiss_fcd' | 'manual'` — all raw strings switched on in 10+ places, with `_` fallbacks that silently swallow typos. Dart enums with `name` serialization are free.

### 7.5 ⚪ Misc
- `capture_controller.dart` is a placeholder comment; capture orchestration (300+ lines incl. API calls and persistence) lives in the widget — the file documents the intent, the code never followed.
- `riverpod_annotation`/`riverpod_generator`/`build_runner` are dependencies but no generated providers exist — unused build complexity.
- `AppDatabase` mixes three concerns (meals DB lifecycle, asset-DB copying, schema). Fine at this size; split before it grows.
- Routes pass `Map<String, dynamic>` extras with stringly keys in 4 places (`'prefillName'` vs `'name'` for the *same payload* in `barcode_result_screen.dart:282-301`) — typed argument classes would have caught that asymmetry.

## 8. UI/UX

### 8.1 🟠 "Restart the app" as a workflow
Both restore-backup and clear-history end with a snackbar telling the user to restart manually (`settings_screen.dart:205-211, 256`). Killing/restarting an app is not a discoverable operation for most users; until they do, the app runs on a deleted/stale database (§4.5). Re-initialize in-process: `closeAll()` → invalidate the provider container → router refresh.

### 8.2 🟡 Accessibility
- Emoji-as-UI throughout (🍴/🔪/🥄 toggles, 🍳 placeholders, 🔥 streak) with no `Semantics` labels — screen readers read nothing useful; emoji rendering varies by device.
- `_StepButton` (`ingredient_card.dart:291-303`) is a bare 18px `GestureDetector` icon — far below the 48dp minimum touch target; the star toggle in history rows (16px) likewise.
- Custom shutter/gallery buttons are unlabeled `GestureDetector`s.
- Low-contrast text on camera overlay (`Colors.white38` on black, 11-12px).
- Hardcoded `fontSize` everywhere ignores the user's text-scale preference in several fixed-height containers (44px recent-meals strip will overflow at 1.3x).

### 8.3 🟡 No localization, despite an explicitly Swiss audience
The app bundles the *Swiss* Food Composition DB, searches its German/French columns, prices in CHF — and every UI string is hardcoded English with default-locale `DateFormat` (no locale passed; `intl` is already a dependency). If de/fr users are the audience, wire up `flutter_localizations` + ARB now; retrofitting 38 files later is much more expensive.

### 8.4 🟡 Input-validation friction and silent data-quality holes
- `digitsOnly` formatters on kcal fields (`barcode_result_screen.dart:366, 596`) forbid decimals — many labels say e.g. "44.5 kcal"; meanwhile other numeric fields allow `1.2.3` (`[\d.]` filter, `double.tryParse` silently fails and the last value sticks with no error shown).
- Manual barcode entry allows logging with 0 kcal and no warning (`:499` defaults blank to 0) — a meal that quietly undercounts the day.
- Amount fields clamp inconsistently: `(0, 9999)` in barcode result, `(1, 9999)` in meal builder — 0g items are loggable in one flow.

### 8.5 ⚪ Polish
- No dark theme; the all-black capture tab recolors the shared `NavigationBar` per-index (`app_router.dart:168-176`) — a theme-level solution (per-branch `NavigationBarTheme` or dark scheme) would be cleaner.
- Search ignores active filters: typing a query drops starred/meal-type/day filters without saying so (`meals_repository.dart:163-165`).
- CSV export omits meal name, notes, macros and price — the columns users most likely want in a spreadsheet.
- The "On-device model (coming soon)" label in settings advertises vaporware.
- `errorBuilder` shows raw `state.error` to the user (`app_router.dart:146-148`).

## 9. Testing

🟠 **Effectively zero coverage.** One smoke test (`widget_test.dart`) pumps a single frame. Meanwhile the codebase contains exactly the kind of pure logic unit tests are cheap for and this review found bugs in:

- `GeminiService._parseAndEnrich` / `_repairTruncated` (JSON repair edge cases)
- `Meal.sumItemMacros`, `Recipe.computeKcalPer100g`, `detectTypeFromTime` (boundary hours)
- `MealsRepository` aggregates (day boundaries, streaks — §4.3 would have been caught by a test with a UTC+1 fixture) via `sqflite_common_ffi` in-memory DBs
- `ResultsNotifier.deleteItem` index remapping (§5.3)

The repository/service layer's concrete-singleton design (§7.2) is the main obstacle; in-memory sqflite removes most of it without interfaces.

## 11. What's done well

Worth keeping and building on:
